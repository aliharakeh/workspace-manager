# Workspace Manager

Wails v2 desktop app. Go owns the window, SQLite, process runner and OS integration; the React UI in `frontend/` talks to Go through Wails bindings and events.

## Layout

| Path | Role |
|---|---|
| `main.go`, `app.go`, `events.go` | Wails entry point, `App` lifecycle, event emission. |
| `bind.go` | API surface: exported `App` methods bound to the UI. |
| `services/` | Runner, templates, ready URLs, notifier, AI. |
| `lib/` | fs, parse-env, import-formats, package scripts. |
| `native/` | OS helpers (process, ports, editor, browser, run) and `pty*.go`, the pseudo-terminal (ConPTY on Windows, `creack/pty` elsewhere). |
| `db/` | SQLite via sqlc: `schema.sql` (final schema, also run at startup), `queries.sql`, generated code. |
| `types/` | UI types (JSON tags match `frontend/lib/types.ts`). |
| `frontend/` | React UI (Vite). Own `package.json`; Bun is the package manager. |
| `frontend/host.ts` | Adapter the UI imports via `frontend/lib/api.ts`: Wails bindings + `EventsOn("runnerEvent")`. |
| `frontend/wailsjs/` | Generated by Wails. Do not edit by hand. |
| `build/` | Wails packaging assets (icons, manifests, installer). |

## Rules

- Adding or changing an API method: edit the `App` method in `bind.go`, run `wails generate module` from the repo root, then update `frontend/host.ts` and any UI callers. Keep Go JSON tags in sync with `frontend/lib/types.ts`.
- Schema or query changes: edit `db/schema.sql` / `db/queries.sql`, then run `sqlc generate` from the repo root. `schema.sql` is embedded and run at every startup with `IF NOT EXISTS` statements, so it only creates missing tables: it does not alter existing ones. There is no migration system; a change to an existing table needs explicit upgrade code.
- A config set holds three command lists of the same shape: a **run** config (starts the app), a **build** config (builds it) and a **setup** config (prepares it, e.g. installs dependencies). They live in `run_configs`/`run_commands`, told apart by `run_configs.kind` (`types.KindRun` / `KindBuild` / `KindSetup`); the `db` and `RunConfigGet/Save` APIs take the kind. An app has one runner session at a time (`RunnerRun` / `RunnerBuild` / `RunnerSetup` fail while any is going) because all apply and restore templates; a build or setup skips ready-URL and idle detection. Setup has no button in the app header, sidebar or workspace card: it runs from the Run/Stop button inside its own panel (`CommandConfigPanel` with `kind="setup"`), which saves the draft first. Config sets created before setup existed get their setup config lazily (`GetOrCreateRunConfig`). `addRunConfigKind` in `db/schema.go` upgrades old databases.
- Apps are listed by `apps.sort_order` (per workspace), not by name: new apps go last and `AppsReorder` (drag-and-drop on the workspace screen) rewrites the order. The UI must not re-sort apps by name. `addAppSortOrder` in `db/schema.go` upgrades old databases.
- Run-config and blueprint commands run on a pseudo-terminal (`native.StartPty`), so output is raw terminal bytes, not lines. It reaches the UI base64-encoded: `LogEvent`/`RunnerOutput` for runs (with byte offsets so a late terminal can catch up), `BlueprintLogEvent` for blueprints. The UI renders both with `frontend/components/terminal.tsx` (xterm.js): run logs are read-only and never write to the command's input; the blueprint dialog is interactive (`BlueprintsSendInput`, `BlueprintsResize`). Line-based logic (ready-URL detection) works on a plain-text copy made in `services/terminal.go`.
- The blueprint AI agent (`services/blueprintai.go`, bound as `BlueprintsAIPropose`) is separate from the app config agent in `appai.go`. It delivers a blueprint only through its `propose_blueprint` tool, which validates and returns errors to the model; nothing is saved until the user clicks Save in the editor. Its system prompt and `validateBlueprintProposal` restate how the runner in `services/blueprints.go` behaves (placeholders, cwd per command, `create_folder`, non-interactive commands, `cmd.exe` vs `sh`). When you change the runner or the placeholder set, update them too (placeholders also live in `renderCommand` in `new-app-from-blueprint-dialog.tsx`).
- The app **Git** tab (`frontend/components/git-panel.tsx`) and the app AI agent share `services/git.go` (shells out to `git -C <project path>`): `git fetch --all --prune` and worktree list/add/remove/prune. The main worktree and the app's own worktree can never be removed. A worktree can run the app's setup/run/build config (`GitWorktreeStart` → `Runner.StartIn`) with any of the app's config sets (picked per worktree in the panel, remembered in `localStorage`; default the active set): it is still the app's one runner session, but commands run and templates are applied/restored in the app's folder inside that worktree (same subfolder of the repo, see `WorktreeAppDir`), and `StatusEvent.worktree`/`configSetId` name them. A session keeps the config set it started with (`session.setID`), so env, commands, and template apply/restore never re-resolve the active set mid-run. In the agent, `git_fetch_all`/`prune_worktrees`/`list_worktrees`/`list_branches` run immediately, but `add_worktree`/`remove_worktree` only stage `AppAIPatch.worktrees`, which the UI runs on Apply (`applyAppAIPatch`).
- Notification setting keys live in both `services/notifier.go` and `frontend/lib/notifications.ts`; keep them in sync.
- Dialogs and `openExternal` use the Wails runtime.

## Commands

From the repo root:

```bash
wails dev                       # Wails + Vite (port 5174)
wails build                     # production native app → build/bin
wails generate module           # regenerate frontend/wailsjs after Go changes
sqlc generate                   # regenerate db after schema/query edits
go test ./db/... ./lib/... ./native/... ./services/...
```

From `frontend/`: `bun install`, `bun run dev`, `bun run build`, `bun run lint`, `bun run typecheck`.
